Инструкции по безопасному деплою и отладке бота (Railway / локально)

Важно — безопасность
- Никогда не выкладывайте BOT_TOKEN или API-ключи в публичные чаты или репозитории.
- Если токен/ключ случайно опубликован — немедленно отзовите/перегенерируйте его в соответствующем сервисе.

1) Немедленное действие: отозвать скомпрометированный токен
- Откройте Telegram -> @BotFather
- Выберите ваш бот -> "API Token" -> Revoke/Regenerate token
- Сохраните новый токен безопасно (менеджер паролей)

2) Установка переменных окружения в Railway
- Откройте ваш проект на Railway
- Перейдите в Service -> Variables (или Environment)
- Добавьте/обновите переменные:
  - BOT_TOKEN = <ваш новый токен>
  - DATAGRAB_API_KEY = <ваш ключ Datagrab>
  - DATAGRAB_ENDPOINT = https://api.datagrab.ru    # если у вас кастомный endpoint
  - OWNER_ID = 6781252224                          # пример вашего ID
  - (опционально) WEBHOOK_URL = https://<your-host>/bot/<some-path>
  - (опционально, для диагностики SSL) DATAGRAB_VERIFY_TLS = 0

- Сохраните переменные и Redeploy / Restart сервиса.

3) Быстрая проверка 409 Conflict (telegram getUpdates)
- Причина: более одного процесса делает polling с тем же BOT_TOKEN.
- В Railway: убедитесь, что Instances / Scale = 1.
- Если у вас автоматически масштабируется — временно уменьшите до 1.
- Лучшее решение: перейти на webhook (см. ниже).

4) Включение webhook (рекомендуется для продакшена)
- В `bot.py` уже присутствует переключение: если задана `WEBHOOK_URL`, бот запускается в webhook режиме.
- Пример: установите `WEBHOOK_URL = https://<project>.up.railway.app/bot/<SECRET_PATH>`
- После деплоя Telegram начнёт слать обновления на указанный URL — polling не будет использоваться и 409 исчезнет.

5) Что делать при ошибке SSL (CERTIFICATE_VERIFY_FAILED)
- Временное диагностическое решение: установить `DATAGRAB_VERIFY_TLS = 0` в переменных Railway и Redeploy.
  - Это отключает проверку сертификатов — Небезопасно, только для диагностики.
- Правильное решение: получить CA-bundle от Datagrab / провайдера и положить его в контейнер, затем
  в переменных установить `DATAGRAB_VERIFY_TLS = /app/certs/ca-bundle.crt` (и удалить временное отключение).
- После получения CA-бundle я могу внести мелкий патч, чтобы код использовал путь к CA, если переменная содержит путь.

6) Локальная проверка
- Скопируйте `.env.example` -> `.env` и заполните значения (не коммитить .env).
- Для теста SSL можно запускать с переменной:

```bash
export DATAGRAB_VERIFY_TLS=0
export BOT_TOKEN="ВАШ_ТОКЕН"
export DATAGRAB_API_KEY="ВАШ_КЛЮЧ"
python3 bot.py
```

7) Логи и отладка Datagrab 502
- Если после деплоя Datagrab возвращает 502 — соберите логи (там есть тело ответа, мы его логируем).
- Отправьте время/полный HTML-ответ в поддержку Datagrab — 502 чаще всего на стороне их сервера.

8) Безопасность и уборка утечек
- После регенерации токена удалите старые токены из истории (если вы случайно закоммитили токен, обратитесь к инструкции по удалению секретов из git history).
- Проверьте, нет ли токена в других службах/скриншотах/чатах.

Если хотите, могу:
- Подготовить патч для поддержки `DATAGRAB_VERIFY_TLS` как пути к CA (безопаснее).
- Добавить сохранение полного HTML-отката Datagrab в `logs/datagrab/<ts>.html` для отправки в поддержку.
- Подготовить точную `WEBHOOK_URL` и подсказки по её настройке (включая защищённый путь).
